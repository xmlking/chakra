[MCP Toolbox for Databases](https://github.com/googleapis/mcp-toolbox) is Google's open source MCP server for databases. It sits between coding agents and our Postgres database, turning hand-written, parameterized SQL statements into MCP tools instead of letting an agent run arbitrary queries directly against the connection string.

In this repo it's registered as `mcp-toolbox` in both `.mcp.json` and `.vscode/mcp.json`, pointing at a locally running server:

```json title=".mcp.json"
{
  "mcpServers": {
    "mcp-toolbox": {
      "type": "http",
      "url": "http://127.0.0.1:5000/mcp"
    },
    "toolbox-secure": {
      "type": "http",
      "url": "https://toolbox-service-123456789-uc.a.run.app/mcp",
      "headers": {
        "Authorization": "Bearer <your-jwt-access-token>"
      }
    }
  }
}
```

<Callout type="info">
  The toolbox server itself isn't started by these configs — it's a separate local process you run
  yourself (see Install below). Both configs just point the agent at `http://127.0.0.1:5000/mcp`
  once it's running.
</Callout>

### Install

```bash
brew install mcp-toolbox
```

### Manage

Toolbox is configured with a `tools.yaml` file that declares `sources` (databases it can connect to), `tools` (parameterized SQL statements it exposes), and `toolsets` (named groups of tools):

```yaml title="tools.yaml"
sources:
  webapp-db:
    kind: postgres
    host: 127.0.0.1
    port: 5432
    database: postgres
    user: ${TOOLBOX_DB_USER}
    password: ${TOOLBOX_DB_PASSWORD}

tools:
  get-customer-by-id:
    kind: postgres-sql
    source: webapp-dn
    description: Look up a customer by id.
    parameters:
      - name: id
        type: string
        description: The customer id.
    statement: SELECT * FROM customer WHERE id = $1;

toolsets:
  webapp-readonly:
    - get-customer-by-id
```

Run it, pointed at that file, on the port our MCP config expects (`5000`):

```bash
./toolbox --config tools.yaml --port 5000
```

Toolbox watches `tools.yaml` and reloads on change by default — restart isn't needed after editing a tool. Pass `--disable-reload` to turn that off. To get started faster instead of hand-writing every tool, `--prebuilt=postgres` (or `--prebuilt=postgres/<toolset>`) loads Google's built-in generic tools (`list_tables`, `execute_sql`, etc.) for the source.

### Secure

Toolbox gives a coding agent a live path to the database, so treat its config with the same care as a database credential:

<Callout type="warn" title="Use a dedicated, read-only DB role">
  Don't point `tools.yaml` at a superuser (e.g. the local `postgres` role). Create a role scoped to
  `SELECT` on the schemas the agent actually needs, and use that role's credentials for the toolbox
  source instead.
</Callout>

- **Never commit `tools.yaml`** — it can contain a database host, user, and password. Add it to `.gitignore` and interpolate secrets with `${ENV_VAR}` syntax (as above) rather than hardcoding them.
- **Prefer hand-written `tools` over `--prebuilt`/`execute_sql` for anything beyond local exploration.** A parameterized statement like `get-customer-by-id` above can't be used for arbitrary SQL; `execute_sql` can. Scope exposed tools with `toolsets` per client/use case rather than exposing every tool to every agent.
- **Keep the server on localhost.** Our config talks to `127.0.0.1:5000`; don't bind toolbox to `0.0.0.0` or expose it on a shared network unless it's also placed behind authentication.
- **If Toolbox is ever exposed beyond localhost** (e.g. deployed for a shared/production use case), require an `authServices` entry and mark sensitive tools `authRequired` so calls carry a validated OIDC token:

  ```yaml title="tools.yaml"
  authServices:
    webapp-auth:
      kind: google
      clientId: ${GOOGLE_CLIENT_ID}

  tools:
    get-customer-by-id:
      authRequired:
        - webapp-auth
  ```

- **Rotate credentials** used by the toolbox source the same way you'd rotate any other database credential, and prefer a secret manager over plain environment variables in shared/production environments.
