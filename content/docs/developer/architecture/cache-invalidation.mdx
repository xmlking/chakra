---
title: Tag-Based Cache Invalidation
description: Organization-scoped cache invalidation over PostgreSQL LISTEN/NOTIFY and SSE.
---

Tag-based cache invalidation connects transaction-bound PostgreSQL notifications to each browser's
TanStack Query cache. Cache invalidation events contain identifiers and tags only; the server derives
the organization scope from the authenticated session rather than accepting an organization id from
the browser.

## Architecture

```text
Mutation transaction           PostgreSQL              Web app instance             Browser
        │                          │                           │                       │
        ├── write data             │                           │                       │
        ├── NOTIFY via tx ────────▶│                           │                       │
        │                          ├── LISTEN event ──────────▶│                       │
        │                          │                           ├── SSE ───────────────▶│
        │                          │                           │                       └─ invalidate
        │                          │                           │                          matching
        │                          │                           │                          query tags
```

The web app uses **Server-Sent Events (SSE)** because invalidations flow only from server to
browser. The browser's native `EventSource` reconnects automatically. WebSocket support is
unnecessary for this one-way stream.

## Publishing from a transaction

`publishCacheInvalidation` publishes through the Drizzle transaction executor. PostgreSQL only
delivers the invalidation after the underlying data change commits; rollback discards both:

```ts
await db.transaction(async (tx) => {
  await tx.update(projects).set({ name }).where(eq(projects.id, projectId));
  await publishCacheInvalidation(tx, organizationId, ["projects", `project:${projectId}`]);
});
```

Always use the organization id already authorized by the mutation. Tags describe affected query
sets or entities, for example `projects` for a list and `project:<id>` for a detail query. Keep
payloads small; PostgreSQL limits `NOTIFY` payloads to 8000 bytes.

## Subscribing and invalidating TanStack Query

`GET /api/cache-events` requires an authenticated session with an active organization. It does not
accept an organization id from the request. Each stream receives only events matching that session's
active organization. The client checks the organization again before invalidating queries.

Organization data queries should include the organization id in their query key and use query
metadata to associate tags:

```ts
queryOptions({
  queryKey: ["organization", organizationId, "projects"],
  queryFn: () => listProjects(organizationId),
  meta: organizationCacheMeta(organizationId, ["projects"]),
});
```

Including the organization id in the query key prevents one organization's cached result from being
reused when the user switches organizations. The metadata is used to match invalidation tags.
Queries without organization/tag metadata are not affected.

When an SSE connection opens or reconnects, and when the server's EventBus reconnects to Postgres,
the client invalidates all cached queries tagged for its active organization. This recovers from
notifications missed during either kind of disconnect. For each received event, only queries in
that organization with at least one matching tag are invalidated.

## Delivery guarantees

The stream is a bridge over the existing [EventBus](./event-bus). `LISTEN`/`NOTIFY` is not durable:
events published while a web instance is disconnected can be lost. The reconnect-time organization
invalidation and normal query stale/refetch behavior limit the effect of missed events. Keep
appropriate query `staleTime` and server-side cache TTLs; this mechanism is a freshness optimization,
not a substitute for authorization or tenant scoping.
